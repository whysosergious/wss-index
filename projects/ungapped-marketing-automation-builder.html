Ungapped · Stockholm

The builder that had to never lose a campaign

Three years inside a marketing SaaS, building the canvas where other people's revenue gets orchestrated — and learning what "production-safe" really means when a bug costs someone their Black Friday.

When I joined Ungapped in March 2021, the automation builder was the kind of feature everyone demos and nobody wants to own. Marketers built campaigns as rigid step lists, and anything with real branching — wait two days, did they open it, if yes do this, if no do that — turned into a pile of disconnected settings pages. My job, over the next three years, became making that complexity visual, fast, and safe to run every single day.

The stakes were personal quickly. These weren't toy workflows: the builder orchestrated real email delivery to real customer lists, some with hundreds of thousands of contacts. If preview showed one thing and production did another, somebody's launch day was ruined. That one fear shaped almost every technical decision I made.

The goal

Give marketers a drag-and-drop canvas — triggers, delays, conditions, actions — that handles genuinely complex user flows and high-volume data, while unifying the three editors (email, survey, landing page) and the reporting behind it. On the backend: C#/.NET services and Azure Functions for delivery, subscriber synchronisation and analytics, with MSSQL underneath.

Sounds like a normal SaaS roadmap. The hard part was never any single feature. It was the combination: visual editing, deterministic execution, and half-a-million-row lists, all at once, without the app falling over.

What kept me up at night

Three things, honestly. First, preview versus production. A marketer tests a flow on ten contacts, it looks perfect, then it runs on 200,000 and behaves differently — a race between a delay node and a condition, a contact re-entering a flow twice. I decided early that the flow must be evaluated deterministically: same graph, same order, same result, every time. Cycles rejected at publish, not discovered at 2am.

Second, segmentation speed. "Show me engaged Stockholm contacts from the last 30 days" took the better part of a minute on big accounts. Nobody builds campaigns with a tool that slow — they go back to spreadsheets. I spent a full sprint with query plans, covering indexes and a pre-computed attributes table until the same reports came back in about two seconds.

Third, imports that never finish. A 500k-contact list import would run as one giant job, fail at 90%, and leave the list in a mystery state. I broke synchronisation into small idempotent chunks as Service Bus–triggered Azure Functions: any chunk can retry or resume, and re-running the whole import is safe by construction.

"Same graph, same order, same result — a marketer should be able to trust the canvas the way a pilot trusts the instruments."

The piece of code that saved us

This is the heart of the builder: topological evaluation of the flow graph. Every node — trigger, delay, condition, action — runs in dependency order, delays are resolved against the contact's own timeline, and any cycle fails loudly at publish time instead of looping in production. The animated stats components and the editors all sit on top of this guarantee.

// flow-engine.ts — deterministic evaluation of automation flows
// Same graph + same contact state = same result. Always.
type NodeId = string;
interface FlowNode {
  id: NodeId;
  kind: 'trigger' | 'delay' | 'condition' | 'action';
  next: NodeId[];
  runAt?: string; // resolved per contact, e.g. "2024-03-01T09:00Z"
}

export function orderNodes(nodes: FlowNode[]): FlowNode[] {
  const byId = new Map<string, FlowNode>(nodes.map(n => [n.id, n]));
  const visited = new Set<NodeId>();
  const ordered: FlowNode[] = [];

  const visit = (id: NodeId, stack: NodeId[]): void => {
    if (stack.includes(id)) {
      throw new Error(`Cycle rejected at publish: ${[...stack, id].join(' → ')}`);
    }
    if (visited.has(id)) return;
    visited.add(id);
    for (const next of byId.get(id)?.next ?? []) visit(next, [...stack, id]);
    ordered.unshift(byId.get(id)!);
  };

  nodes.forEach(n => visit(n.id, []));
  return ordered.sort(byScheduledTime); // delays resolved per contact
}

That little throw on cycles is my favourite line in the whole codebase. It turned an entire class of 2am incidents into a red message in the editor, exactly where it belongs.

How it landed

By the time I left in early 2024, the builder was the daily driver for campaign creation — flows people actually trusted with launches. Segmentation reports that used to take ~40 seconds came back in ~2. Imports resumed instead of restarted. And the email, survey and page editors finally felt like one product instead of three cousins.

What I'd do differently

I would have versioned published flows from day one — immutable snapshots per publish, so a marketer could diff "what changed between Tuesday's send and today's". We approximated it with drafts, but true time-travel debugging would have been worth the storage.
