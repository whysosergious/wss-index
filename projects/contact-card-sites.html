Local trades

One page, one trade, one number

A small batch of single-page sites for plumbers, electricians and carpenters: real photos, a real service area, tap-to-call, and a vCard that saves the details to a phone. One template underneath, each site owned by the person it belongs to.

The brief was always the same and almost always the same six questions: who are you, what do you do, where do you work, how do I reach you, and can I see proof you exist. Most of these people had either nothing online or a page from 2011 built by a cousin, loading slowly and telling nobody where they actually worked.

So I stopped treating each site as a project and started treating it as a template with four editable variables. One page, no framework runtime, no build step, no hosting bill beyond a domain — and an owner who can change their own phone number in a text file without asking me.

The goal

A page that loads instantly on a phone with one bar of signal, shows the work rather than stock photography, and makes calling the easiest possible action. Plus the small things that quietly decide whether it's found at all: a title that names the trade and the town, a local service-area list, and a vCard download.

Why one page was enough

Nearly every site I was replacing had a nav bar with five items and four of them were empty. Stripping it back was the most useful thing I did: one page that answers everything, with a call button that is a real tel: link so it works from the search result, not only from the page.

The other decision was to make the sites static and owned. No CMS, no database, no login. The content lives in the repository, the owner gets push access, and a site that is a handful of files cannot be slow, cannot be hacked into a spam server, and cannot need me to keep it alive. If the owner stops wanting it, deleting it is one git rm.

"A page that answers every question on one screen beats a five-item navigation bar with four empty pages."

The piece of code that saved us

Not the design — the build. The whole template compiles to a folder of static files, which means a new trade is a data file, not a project. Everything the owner can change is a field; everything I control is in the template and never appears in their copy.

// build.mjs — a trade is a data file, not a project
import { readFile, writeFile } from "node:fs/promises";

const SITE = {
  name: "Erik Lindqvist",
  trade: "Electrician",
  phone: "+46 70 123 45 67",
  areas: ["Hammarby Sjöstad", "Södermalm", "Djurgården"],
  works: ["img/panel-1.jpg", >"img/panel-2.jpg"],  // real jobs, real photos
};

const vcard = [
  'BEGIN:VCARD', 'VERSION:3.0',
  `FN:${SITE.name}`, `TEL;TYPE=CELL:${SITE.phone}`,
  'END:VCARD', '',              // trailing newline: some phones need it
].join('\r\n');

await writeFile("dist/${slug}/contact.vcf", vcard);
await writeFile("dist/${slug}/index.html", render(SITE));

// The title is the whole SEO strategy, so it's generated, not typed.
const title = `${SITE.trade} in ${SITE.areas[0]} — ${SITE.name}`;

Generating the page title from the trade and the first service area is the entire search strategy. It is also the thing every hand-rolled one-pager gets wrong, because a title of "Home" tells nobody anything.

How it landed

Calls started coming from the first hour the pages went live, because a page with a tap-to-call button removes a step. Load times dropped from multi-second to instant on mobile data, and the owners can change their details themselves — which, for work this small, is the difference between a site that stays correct and a site that quietly shows a phone number from 2022.

What I'd do differently

I would have asked for a written list of recent jobs on day one. Photos were the bottleneck in every single build, and I lost more time chasing images than writing markup. Getting them before the first meeting is the entire lesson.
