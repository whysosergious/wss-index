Billing back-office

The month-end that used to take a day

Invoices that write themselves from the contracts they belong to, carry sequential numbers, and chase the ones nobody pays. Month-end became a report instead of a copying session.

A small service company with recurring contracts had an invoicing routine that nobody enjoyed. Once a month, someone opened four spreadsheets, copied line items into a Word template, generated PDFs by hand, renamed them consistently, emailed them, and then spent the rest of the week remembering to chase the ones that weren't paid. The work was the same every month, which is the definition of work a computer should be doing.

What I built is not glamorous: a nightly job that looks at which contracts are due, writes the invoice, issues it a proper number, and emails it. Then a smaller job that looks at which invoices are unpaid and, after a polite interval, sends a reminder — and stops.

The goal

Invoices generated from the contract that already exists, numbered without gaps, sent on schedule, and chased on a schedule that stops. Plus a month-end view that says what was billed, what was paid and what is still out — from the same data, with no second spreadsheet.

The spreadsheet era

Two things carried all the risk. Invoice numbers were assigned by hand, and duplicates are the kind of mistake an accountant notices immediately and a customer notices later. Numbers now come from a single database sequence inside the transaction that writes the invoice, so a retried run cannot mint a second number.

Second, chasing customers is a tone problem. The old reminders were a fixed template fired by hand, which is how a politely worded email turns into an aggressive one if you send it twice. Reminders are now tied to the invoice's own state: one before the due date, one after, then silence — and a customer who replies stops the sequence immediately.

"A retried billing run must never mint a second invoice number. That's the whole ballgame in one guarantee."

The piece of code that saved us

The billing run. It is idempotent by contract — every invoice is keyed by its billing period, so running it twice in a day produces one invoice, not two, and running it after a crash picks up exactly where it stopped.

// billing-run.ts — nightly, idempotent, one number per invoice
export async function runBilling(asOf = new Date()) {
  const due = await contracts.billableIn(asOf);  // next period, prorated, one row per contract
  const result = { issued: 0, skipped: 0, failed: [] };

  for (const contract of due) {
    // (contract_id, period) is unique — the guard, not the intention.
    const existing = await invoices.find(contract.id, contract.period);
    if (existing) { result.skipped++; continue; }

    try {
      const invoice = await db.transaction(async (tx) => {
        const number = await tx.nextInvoiceNumber();  // sequence, inside the tx
        return tx.invoices.insert({
          number, contractId: contract.id, period: contract.period,
          lines: await tx.priceContract(contract),
        });
      });

      await mail.sendInvoice(invoice);
      result.issued++;
    } catch (err) {
      // One bad contract must not stop the other forty.
      result.failed.push({ contract: contract.id, error: err.message });
    }
  }

  return result;
}

The per-contract try/catch is the unglamorous line that matters most. A single malformed contract used to mean the whole month's run stopped halfway, with no record of which invoices had already gone out.

How it landed

Month-end is now a report: billed, paid, outstanding, overdue, all agreeing with the bank. Reminders go out on their own and stop when a customer answers. Nobody copies between spreadsheets, because there is only one place the numbers live.

What I'd do differently

I would have added a reconciliation against the bank feed before shipping the first version. Invoice numbers being correct and the money actually arriving are two different claims, and it took me a while to notice I was only proving the first one.
