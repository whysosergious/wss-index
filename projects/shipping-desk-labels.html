Shipping automation

Forty parcels a day, forty minutes back

An online shop where every shipment is one action: the address gets checked, the carrier gets booked, the label comes out of the printer and the tracking number lands back on the order before the packing is finished.

This shop sends somewhere between twenty and fifty parcels a day, and every single one of them used to cost five to seven minutes of someone's morning. Read the address off the order, check it by hand, look up the customer in the carrier's website, book the shipment, print a label, then update the order with a tracking number. Five systems, one human, and no way to tell afterwards whether any of it actually happened.

Shipping is the perfect candidate for automation because it is the rare process where the rules are already written down — they are just written down in a carrier's API and in the habits of whoever did it first. My job was to make one action mean all five steps.

The goal

One click in the order screen that validates the address, books with the carrier, produces a printable label and writes the tracking number back — with a clear failure state whenever any of those steps can't be trusted.

The forty minutes nobody had

Two things made this harder than it looks. First, bad addresses are not rare and are not always wrong. "Second floor, back entrance" is not an invalid address, it's a note. Anything the validator can't resolve automatically gets flagged and held, never guessed — a parcel that arrives is worth more than a label that printed in half a second.

Second, the carrier's API fails in boring ways. Rate limits, a five-second timeout, a service that is temporarily unavailable. None of those are errors you can show a customer, so every call is retried with backoff, and a shipment that can't be booked stays visibly unbooked in the order list instead of silently disappearing into a queue nobody watches.

"Never guess an address to make a label print faster. A slow shipment is a conversation; a parcel at the wrong house is a refund."

The piece of code that saved us

One endpoint that owns the whole sequence and records each step, so a half-finished shipment is a visible state rather than a mystery. The order table doesn't have a "shipped" boolean; it has a small state machine.

// ship-order.ts — one call, five steps, every step recorded
type ShipStep = 'validating' | 'booking' | 'labelled' | 'done';

export async function shipOrder(orderId: string) {
  const order = await loadOrder(orderId);
  const check = await validateAddress(order.address);

  if (!check.resolved) {
    // Hold it. Do not book, do not print, do not guess.
    return markOrder(orderId, 'needs_address_review', check.notes);
  }

  const booking = await retry(() => carrier.book({
    address: check.normalised,          // carrier's own form, not ours
    parcel: { weightG: order.weightG, ...order.dimensions },
  }), { attempts: 3, backoffMs: 400 });

  // Tracking goes back to the order before the label prints —
  // if the printer is down, the customer still has a number.
  await saveTracking(orderId, booking.trackingNumber);
  await renderLabel(booking.labelUrl);

  return markOrder(orderId, 'ready_to_post', booking);
}

Writing the tracking number back before printing is the ordering decision I would defend hardest. Printers fail; carriers don't lose bookings. The customer gets a number either way.

How it landed

Shipping is now a single action that takes seconds, and the tracking number is on the order before the box is sealed. Address problems stopped being discovered three days later by a courier standing at the wrong door — they show up as a review task in the morning. Manual shipping work is effectively gone.

What I'd do differently

I would have built the label preview before the booking integration. I spent longer than I'd like to admit on a printer driver, and a label preview in the browser would have found most of it in an afternoon.
