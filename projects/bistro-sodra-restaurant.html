Friday night, forty covers, zero paper tickets

A Södermalm restaurant where guests order from their phones, the kitchen works off screens, and the smudged-paper wrong dish is extinct.

By Sergio Stankevich · Freelance full-stack build

The owner told me the story in one sentence: "On Fridays we lose money on the mistakes, not on the food." Waiters re-typing orders into the POS, paper tickets in a hot kitchen, one smudged line — wrong dish, remake, comped dessert, a table that leaves a three-star review for food they never actually ordered. I spent two Friday services standing near the pass just watching, and honestly the wonder is that it worked at all.

So we rebuilt the flow around one idea: the guest's phone is the order pad, and everything downstream — kitchen display, reservations, the evening close — reads from the same record. Scan the QR on your table, order, pay. The kitchen sees it in under a second, grouped by station. The host sees the table flip to occupied. Closing time, the numbers already agree.

The goal

Table reservations synced with live table state, QR-code ordering with no app install and no login, a kitchen display split by station (hot / cold / bar), and a POS that stays the source of truth so the evening close is boring. Boring closes were the actual acceptance criterion.

What kept me up at night

First, table mix-ups. No-login QR ordering is wonderful until someone photographs a code, sends it to a friend, or sits down at the wrong table. Every order has to be provably attached to the right table, and codes have to die quickly. I signed each QR payload with HMAC and gave it a short expiry — the dining room equivalent of a session cookie you can't steal by screenshot.

Second, the kitchen can't wait. A display that lags or drops tickets during rush is worse than paper, because at least paper is honest about being there. Orders fan out over WebSockets per station with acknowledgement, and a reconnected screen re-fires anything it missed. Under a second from phone tap to kitchen screen, measured, not hoped.

Third, the host's nightmare: double-seating. Reservations, walk-ins and lingering tables all disagreed. One query — one view — now answers "what is the state of every table right now", and the floor map reads nothing else.

"The evening close should be boring. If closing is exciting, something upstream is broken."

The piece of code that saved us

Table sessions. This small module is the trust anchor of the whole system: it mints the QR tokens, verifies them on every order, and rejects anything expired, forged, or attached to a table that has since been closed and reopened. Every challenge above — mix-ups, screenshots, wrong tables — funnels through these forty lines.

// table-session.ts — the trust anchor: who ordered, and where are they sitting?
import { createHmac, timingSafeEqual } from 'node:crypto';

const SECRET = process.env.QR_SECRET!; // rotated nightly
const TTL_SECONDS = 4 * 60 * 60; // one service; screenshots expire

export function mintTableToken(tableId: string, serviceDate: string): string {
  const exp = Math.floor(Date.now() / 1000) + TTL_SECONDS;
  const payload = `${tableId}.${serviceDate}.${exp}`;
  const sig = createHmac('sha256', SECRET).update(payload).digest('base64url');
  return `${payload}.${sig}`; // encoded into the table QR
}

export function verifyTableToken(token: string, serviceDate: string): string {
  const [tableId, date, exp, sig] = token.split('.');
  if (date !== serviceDate) throw new Error('QR is from another service');
  if (Date.now() > Number(exp) * 1000) throw new Error('QR expired — ask staff for a fresh one');

  const expected = createHmac('sha256', SECRET)
    .update(`${tableId}.${date}.${exp}`).digest('base64url');
  const a = Buffer.from(sig ?? ''), b = Buffer.from(expected);
  if (a.length !== b.length || !timingSafeEqual(a, b)) {
    throw new Error('Invalid table code');
  }
  return tableId; // every order line is stamped with this
}

The service-date binding is the detail I'm proudest of: even a perfect screenshot of today's QR is useless tomorrow. Staff reprint codes with the morning setup, and yesterday's photos become souvenirs.

How it landed

Order errors fell off a cliff — roughly 85% down, because the kitchen reads what the guest wrote, not what a waiter deciphered. Tables turned about 20% faster at peak since payment closes the table instead of flagging someone down. And the owner got his boring closes: the POS, the kitchen and the reservations finally tell the same story.

What I'd do differently

I'd have built the offline story sooner. When the Wi-Fi hiccuped during the first busy Saturday, ordering paused for ten minutes. A small queue-and-retry on the guest side would have made it a non-event instead of a war story.
