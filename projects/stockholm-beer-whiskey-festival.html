Two days, three hundred pours, one live tap list

The platform behind Stockholm Beer & Whiskey Festival: timed tickets that can't oversell, exhibitors running their own pour lists, gates that scan without Wi-Fi, and a leaderboard the whole hall watches.

By Sergio Stankevich · Freelance full-stack build

I went to the festival the year before I built for it, and I spent half my time in the wrong queues. The tap list was paper taped to stands, half of it outdated by evening. Some pours ran out silently; the good stuff drew lines you couldn't see until you'd already joined them. The organisers, meanwhile, ran tickets in one system, exhibitors in spreadsheets, and learned what worked weeks later from a survey. Everybody was guessing — guests, pourers, organisers. I kept thinking: this whole event is an information problem wearing a beer costume.

So the next year, we fixed the information. Timed-entry tickets capped the crowds per hour. Exhibitors managed their own pours from their phones — kicked keg, two taps, you're on the map instantly. Visitors rated live, the leaderboard updated on the big screens, and the gates scanned signed tickets that didn't care whether the Wi-Fi was alive. For two days, three hundred pours were exactly where the system said they were.

The goal

One platform for three crowds: visitors who want to find great pours without blind queues, exhibitors who want to manage their stand without paperwork, and organisers who want full halls without overcrowding — plus analytics afterwards that actually say what happened. Tiered ticketing, exhibitor portal, interactive venue map, live ratings, all of it.

What kept me up at night

First, overselling a time slot. A festival hall has a fire limit, not a vibe limit. If two people buy the last ticket to the same hour at the same second, somebody gets turned away at the door — the worst possible experience. Booking runs inside a row-locked transaction: check capacity, create the Stripe session, increment, commit. The database is the bouncer, and it never blinks.

Second, the dead gate. Festival Wi-Fi dies the way festival Wi-Fi does — right at peak entry, obviously. So tickets are signed tokens the scanners verify offline: valid signature, right slot, not seen before. Scans queue locally and sync when the network returns. Replays get rejected on the spot. The queue kept moving through a full outage on Saturday, which is my favourite sentence in this whole story.

Third, stale pour lists. A leaderboard is only magic if it's true. Exhibitors toggle their own pours — kicked, pouring, back on — and the ratings wall recomputes live from the pour ledger. No organiser middleman, no paper, no "is this still on?" pilgrimages across the hall.

The piece of code that saved us

The slot booking plus the offline gate check, together. The first makes overselling structurally impossible; the second keeps entry moving when the network doesn't. Between them they cover the two moments a festival lives or dies by: selling the ticket, and honouring it.

// festival-entry.ts — sell honestly, scan anywhere
export async function bookSlot(slotId: string, email: string) {
  return await db.tx(async (t) => {
    // Lock the slot row: concurrent buyers queue here, not at the door.
    const slot = await t.one(
      `SELECT capacity, sold FROM slots WHERE id = $1 FOR UPDATE`, [slotId]);
    if (slot.sold >= slot.capacity) throw new Error('This hour is full — pick another');

    const ticket = await stripe.checkout.create({ slotId, email });
    await t.none(`UPDATE slots SET sold = sold + 1 WHERE id = $1`, [slotId]);
    return { ...ticket, qr: signEntry({ jti: ticket.id, slotId }) };
  });
}

// Gate scanner: works fully offline. Syncs when the network returns.
const seen = new Set<string>(); // + persisted log for post-event sync

export function verifyEntry(qr: string, nowSlot: string) {
  const t = jwt.verify(qr, process.env.GATE_SECRET!); // ticket id + slot
  if (t.slotId !== nowSlot) throw new Error('Wrong entry hour — see staff');
  if (seen.has(t.jti)) throw new Error('Already scanned');
  seen.add(t.jti);
  queueSync(t); // replays in when Wi-Fi is back; replays of QRs still rejected
  return t;
}

The FOR UPDATE lock is doing all the heavy lifting in part one: without it, two simultaneous buyers both see "one left" and both win. With it, the second simply waits its turn and gets told the truth.

How it landed

Zero oversold slots across the whole weekend. The live leaderboard became the thing people gathered around — exhibitors watched their pours climb in real time, which did more for data quality than any nagging email ever could. Entry survived the Saturday Wi-Fi outage without slowing. And the organisers finally got their analytics while the glasses were still being washed: which hours peaked, which pours won, where the queues formed.

What I'd do differently

I'd add a "still pouring near me" view sorted by walking distance inside the hall. Visitors loved the leaderboard but kept asking the follow-up question — "okay, but where?" — and the map answered it one tap too late.
