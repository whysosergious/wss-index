Wholesale supply

The stocktake nobody dreads

A phone camera that reads barcodes, stock levels that stay honest across two locations, and reorder points that raise their own purchase orders instead of waiting to be noticed.

Stock control at a small wholesaler is a counting problem wearing a costume. The goods are barcoded, the shelves are labelled, and yet the number in the system and the number on the shelf disagree constantly — because every movement between the warehouse, the van and the customer is a note somebody makes in the wrong place. The count itself is the easy bit. It's the twelve hours before the count that are dishonest.

Stockroom makes the movements the source of truth. Scan on the way out, scan on the way in, and the level is whatever those scans say it is. Counting stops being an event and becomes a byproduct. The scanner is the phone already in the person's pocket, because buying dedicated hardware for a problem a browser camera can solve is not a decision I'd defend.

The goal

Live stock per SKU per location, movements captured by scanning rather than remembered, low stock that becomes a draft purchase order on its own, and a stocktake screen that a person can use standing up, in a cold room, wearing gloves.

Counting in a cold room

The design constraint that shaped everything else was the phone in one hand and a box in the other. That rules out tiny tap targets, ruled-out data entry, and any flow that needs precision. It also rules out the classic mistake: making the stocktake a form. So a stocktake is a list you swipe through, and the only question asked per line is count or not — the number comes from the scanner, and a line with no barcode can still be counted by searching its name.

The second real problem is two locations. A van is a location. Stock moves warehouse → van → customer, and the van's stock is the number everyone gets wrong. Treating the van as a stock location instead of an exception made the awkward part ordinary.

The piece of code that saved us

Stock is never stored and then adjusted. It is a projection of movements, which means it can't drift away from the movements that produced it.

// stock.ts — a level is a projection of movements, never a stored number
export async function stockAt(sku: string, locationId: string) {
  const { rows } = await db.query(
    `SELECT COALESCE(SUM(delta), 0) AS on_hand
       FROM movements
      WHERE sku = $1 AND location_id = $2`,
    [sku, locationId],
  );
  return Number(rows[0].on_hand);
}

export async function raisePurchaseOrders() {
  // Reorder point and pack size live on the product, not in someone's head.
  const low = await db.query(
    `SELECT p.sku, p.reorder_point, p.pack_size,
            SUM(m.delta) AS on_hand
       FROM products p
       JOIN movements m ON m.sku = p.sku AND m.location_id = $1
      GROUP BY p.sku, p.reorder_point, p.pack_size
     HAVING SUM(m.delta) <= p.reorder_point`,
    [WAREHOUSE_ID],
  );

  for (const row of low.rows) {
    const shortfall = row.reorder_point * 2 - row.on_hand;
    // Round up to whole packs — suppliers sell packs, not units.
    const qty = Math.ceil(shortfall / row.pack_size) * row.pack_size;
    await purchaseOrders.draft({ sku: row.sku, qty });
  }
}

Because the level is a sum rather than a value, a bad scan is a mistake you can find. Because the reorder is a function of that sum, a forgotten reorder is a mistake that can't happen twice.

How it landed

Stock numbers stopped being a quarterly surprise. Purchase drafts appear before the shelf is empty instead of after a customer asks. And the stocktake, which used to be a locked room and a clipboard, is now a person walking the aisles on a phone.

What I'd do differently

I would have put the van scan in the driver's normal route from the start. Letting a load leave the warehouse unsanned "just this once" cost me a real argument with a number I couldn't reconstruct.
