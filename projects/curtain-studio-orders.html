Made-to-measure workshop

Nobody retypes a curtain order

Two people used to handle every made-to-measure order by hand — reading dimensions, sketching the shape, pricing it, and emailing a quote. Now the customer configures the curtain, and the order does the rest on its own.

Made-to-measure curtains are not hard because of the fabric. They are hard because of the paperwork. Every order arrived as an email with a half-finished sentence in it, then one person measured, another sketched, someone else typed the numbers into a spreadsheet and guessed a price. The workshop was good. The process around it was pure retyping, and every retyping was a chance to be wrong by ten centimetres.

What replaced it is boring in the best way. The customer picks a style, enters their wall and window measurements, and the site returns a price. Once they pay, everything downstream happens without a human: a scaled drawing goes to the plotter, a job card appears for the seamstress, PostNord gets a label, the invoice is issued, and the customer's account shows the order moving.

The goal

Take the manual order handling out of the loop without taking the customer out of the conversation. Self-service configuration and quoting on the site, and a pipeline behind it that never asks anyone to re-enter a number that already exists somewhere else.

What it replaced

The first version was a spreadsheet with a contact form in front of it. It worked, which is the dangerous part — it looked fine until someone ordered a 214 cm drop, it was cut at 214 and the heading, and the return cost more than the curtain. From then on every measurement lives in the order, and every derived number — fabric drop, heading allowance, seam and hem, price — is calculated once, in one place, and read everywhere else.

The second problem was the handoff. Orders used to be discussed over the phone, so the person cutting had context the system never saw. The job card is that context, written down: measurements, chosen fabric, hardware, delivery date, and a link to the customer's own notes.

"If a number can be derived, nobody should type it twice. Every extra typing is a place for a 10 cm mistake."

The piece of code that saved us

The measurement validator. Curtains are configured by customers, and customers round numbers — "about 210", "roughly two and a half metres". The validator turns a loose input into either a confirmed dimension or a question back to the customer, before anyone at the workshop sees it.

// measurements.ts — loose customer input -> confirmed dimensions
export function resolveDrop(
  raw: { poleCm: number; requestedCm: number },
  fabric: { dropCm: number },
): { dropCm: number; question?: string } {
  if (raw.requestedCm > poleCm - fabric.dropCm) {
    return {
      dropCm: poleCm - fabric.dropCm,
      question: 'That drop is longer than the fabric allows. Shall I use the maximum instead?',
    };
  }

  // Round to whole cm, but flag anything the customer is guessing at.
  const dropCm = Math.floor(raw.requestedCm);
  const isGuess = Math.abs(dropCm - raw.requestedCm) > 0.5 || dropCm % 5 !== 0;

  return {
    dropCm,
    ...(isGuess ? { question: `'${dropCm} cm' is unusual — can you measure the pole again?` } : {}),
  };
}

That question costs the customer ten seconds and saves a return. Every question the site asks is one the workshop used to answer by making a phone call.

How it landed

Quotes come back in seconds instead of two days, and the workshop stopped starting days by reading email. The plotter file, the job card and the shipping label all come out of the same order record, so they cannot disagree with each other. Returns dropped to the ones caused by a wall that isn't straight, which is a measuring-tape problem rather than a software one.

What I'd do differently

I would have put a photo-upload step on the window early. Half the measurement disputes were never about the number — they were about a window frame that isn't where the customer thought it was.
