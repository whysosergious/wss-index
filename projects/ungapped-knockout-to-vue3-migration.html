Ungapped · Stockholm

Rewriting the plane mid-flight

How we moved a large marketing platform off KnockoutJS without freezing releases — one route at a time, with both frameworks living side by side for months.

Every legacy codebase has a moment where adding a button takes a week and everyone just… accepts it. For our KnockoutJS frontend, that moment had arrived by 2022. Viewmodels hundreds of lines long, observables subscribing to observables, nobody able to say what re-renders when. New developers needed weeks just to stop being afraid of it. I led the migration to Vue 3 — and the rule from day one was: the product ships every week, migration or not.

That rule killed the obvious approach. No big-bang rewrite, no feature freeze, no "we'll be back in six months with something beautiful". Instead we did the strangler-fig thing for real: the old Knockout shell learned to mount new Vue islands, and route by route, the islands took over until there was nothing left to strangle.

The goal

Replace a large KnockoutJS codebase with Vue 3 + TypeScript: Composition API, Pinia stores, typed props, virtualised lists for the 50k-row grids. Cut the time it takes to add features, make performance predictable, and get onboarding from weeks down to days. All while the marketing platform kept releasing.

What kept me up at night

The scary part was never Vue — Vue is lovely. It was the in-between months, when a single page had a Knockout viewmodel owning state that a new Vue component also needed. Two reactivity systems, one truth. Get that wrong and you get the worst kind of bug: the screen shows one thing, the save sends another, and nobody can reproduce it twice.

The second fear was subtler: migrating the shape of the code, not just the syntax. A line-by-line translation of a 600-line viewmodel gives you a 600-line composable nobody understands either. Each route got a small redesign pass — what state is actually shared, what can be local, what can be derived — before a single line was ported.

And third, the long tail. Migrations die at 80%: the last weird reports page nobody wants to touch. We kept a visible checklist per route and made "delete 500 lines of Knockout" a legitimate sprint ticket. Deleting code should feel like progress, because it is.

"The migration is done not when the new code works, but when the old code is gone. Plan the funerals too."

The piece of code that saved us

This bridge is what made the in-between months survivable. A Knockout observable mirrors into a Vue ref, both directions, with subscriptions torn down when the component unmounts — so old and new code share one source of truth without either framework knowing the other exists. The host wrapper below it is how a legacy route mounts a Vue island inside a Knockout template.

// ko-vue-bridge.ts — one truth, two reactivity systems
import { ref, watch, onUnmounted, createApp, h } from 'vue';

export function useKnockout<T>(koObservable: any) {
  const state = ref<T>(koObservable());

  // Knockout → Vue: keep the ref in sync
  const subscription = koObservable.subscribe((v: T) => {
    state.value = v;
  });

  // Vue → Knockout: write back only on real change (no echo loops)
  const stop = watch(state, (v) => {
    if (koObservable() !== v) koObservable(v);
  });

  onUnmounted(() => {
    subscription.dispose(); // leaked subscriptions were bug #1 in dev
    stop();
  });

  return state;
}

// KoHost — mount a Vue island inside a legacy Knockout template
export function mountIsland(el: HTMLElement, component: any, props: object) {
  const app = createApp({ render: () => h(component, props) });
  app.mount(el);
  return () => app.unmount(); // called by the outgoing route
}

The koObservable() !== v guard looks paranoid until you've debugged your first infinite echo loop at midnight. Then it looks like the most important line in the file.

How it landed

Routes flipped one by one with zero freeze releases. Feature work got roughly twice as fast to scope — typed props and small composables instead of archaeology. The big grids stopped janking thanks to windowing. And onboarding a new developer went from "read these viewmodels and pray" to "here are the stores, here's the pattern".

What I'd do differently

I'd record a five-minute video per migrated route explaining what the old code did and why the new shape differs. We wrote docs, but video would have carried the reasoning — the part that actually rots.
