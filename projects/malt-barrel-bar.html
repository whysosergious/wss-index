Beer bar · Gamla Stan, Stockholm

The two-minute close

A Gamla Stan beer bar where tabs open in seconds, regulars get recognised, Swish settles the bill, and closing takes two taps instead of twenty minutes.

I watched the Saturday close at Malt & Barrel once, and once was enough. Paper slips spread across the bar, the card reader doing its little thinking dance, the bartender doing arithmetic that got more creative with every pint he'd served. Twenty minutes, with the last guests standing around watching their evening end in bookkeeping. The owner didn't ask for "a POS system". He asked: "can closing take two minutes?"

So every design decision bent toward that number. Tabs became records, not slips — items, splits, Swish references, loyalty stamps, all attached. Members climbed bronze-silver-gold tiers without anyone stamping a card. And the tab only closes on a signed, verified PAID event from Swish, never on hope.

The goal

Open a tab in seconds, split it fairly between friends, pay by Swish (with BankID where identity matters), recognise regulars with tiers and stamps, and reconcile the evening to the öre in two taps. Swedish payments aren't a plugin here — they're the whole point, so Swish and BankID had to be first-class, not bolted on.

What kept me up at night

First, lost and double-charged tabs. Bar networks flake, staff double-tap, guests retry payments. If "pay" isn't idempotent, someone gets charged twice and tells everyone they know. The tab moves through a tiny state machine — open, pending, closed — where every transition carries an idempotency key. Retries are free; illegal jumps are impossible.

Second, fake paid states. The scariest bug in any payment system is a tab that says "paid" when no money moved. So the close path only fires on a server-verified Swish callback with a matching reference and amount. The UI can show whatever spinners it likes; the ledger only listens to Swish.

Third, loyalty that drifts. Stamp cards live in wallets, memories and arguments. Tiers computed live from the stamp ledger — one query, auditable, no parallel bookkeeping. A guest asking "how many stamps do I have?" gets the same number the bar sees.

"The ledger only listens to Swish. The UI can show whatever spinners it likes."

The piece of code that saved us

The payments module: tab transitions with idempotency keys, the Swish request with its reference, and the callback verification that is the only thing allowed to close a tab and award stamps. Read it as the answer to all three fears above — retries safe, paid states real, loyalty automatic.

// payments.ts — the only path from "open tab" to "closed tab"
type TabState = 'open' | 'pending' | 'closed';
interface Tab { id: string; total: number; state: TabState; lastKey: string | null }

const allowed: Record<TabState, TabState[]> = {
  open: ['pending', 'closed'],
  pending: ['closed', 'open'], // back to open if Swish fails
  closed: [],
};

export function transition(tab: Tab, to: TabState, idemKey: string): Tab {
  if (tab.lastKey === idemKey) return tab; // double-tap? already done.
  if (!allowed[tab.state].includes(to)) throw new Error(`Illegal ${tab.state} → ${to}`);
  return { ...tab, state: to, lastKey: idemKey };
}

export async function requestSwish(tab: Tab, payerAlias: string) {
  const ref = `MB-${tab.id}-${Date.now()}`; // unique per attempt
  await swishApi.createPayment({
    payeeAlias: process.env.SWISH_MERCHANT!,
    amount: tab.total, payerAlias, message: `Malt&Barrel tab ${tab.id}`,
  });
  return transition(tab, 'pending', ref);
}

// The ONLY closer: a verified Swish callback. Nothing else may call this.
export function onSwishPaid(tab: Tab, cb: { ref: string; amount: number; sigOk: boolean }) {
  if (!cb.sigOk || cb.amount !== tab.total) throw new Error('Unverified payment');
  awardStamps(tab); // loyalty lands exactly when money does
  return transition(tab, 'closed', cb.ref);
}

Notice the stamps ride inside the verified close. That ordering — money first, loyalty second, same function — is what makes "where are my stamps?" arguments impossible.

How it landed

The close takes about two minutes now, and it matches to the öre — the owner checked obsessively for the first month and then stopped checking, which is the real review. Returning members are up by about a third, because the bar finally recognises them back. And nobody has been double-charged since launch, which in bar software is the statistic that matters.

What I'd do differently

I'd add bill-splitting by item from the start instead of by amount. Groups always want "I had the IPA and half the fries", and amount-splits cause exactly the bar-counter negotiations software should end.
